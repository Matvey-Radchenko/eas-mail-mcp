# 1.0.0 release acceptance

- Status: draft; not publication evidence
- Release type: direct stable 1.0.0
- npm dist-tags after acceptance: `latest`, then `next` to the same version
- Release commit and immutable staged artifact hashes: pending

## Scope

The release includes the mail, scheduling, diagnostics, and recovery work listed
in [CHANGELOG.md](../../CHANGELOG.md). It preserves the EAS 14.1 security boundary,
bounded content retrieval, per-account write opt-in, and UUID idempotency.
The agreed live scope includes synthetic service messages to the owner's own
accounts and dedicated calendar fixtures. OOF changes require a separate
authorized test window because they affect replies to other incoming mail.

### Development performance

The original sequential benchmark produced both passing and failing relative
latencies with unchanged executables. All reports remain retained: the full
`cargo xtask perf` run passed at ratio 0.760, a later packaged repeat failed at
1.411, and three predetermined repeats produced 0.926, 0.941, and 1.786.
Those short Rust-first/Python-second phases did not retain individual samples,
so the cause of a particular earlier outlier cannot be established.

The benchmark now keeps both sessions alive and warmed up, then measures 200
adjacent request pairs with alternating Rust/Python and Python/Rust order. It
still compares each complete series' p95, with the same 1.15 limit, and retains
all startup and latency observations. Bounds use unrounded values. Six
regression tests check common-load drift, a real 20% slowdown, complete sample
retention, no retry, invalid samples, and the unrounded threshold. No production
code or synthetic-server executable changed for this correction.

Five runs were declared before measurement, after builds and helper CLI checks
finished. All five passed, all process groups exited, and executable hashes
matched before/after. The previously queued `gh` request finished 11.27 seconds
before the first run. The third run included a slower interval for both servers
and was retained. Python was 3.14.4 with MCP 2.0.0 and Pydantic 2.13.4.

### Development calendar and scheduling acceptance

Both provider variants passed the production-backend personal calendar lifecycle:
timed and all-day create/update/delete, and a three-occurrence weekly series
with one occurrence updated twice, another occurrence deleted, and the whole
series deleted. The 11 writes per account returned HTTP 200 and protocol status

returned five one-off suggestions and five weekly patterns covering nine dates,
with a 15-minute buffer and the server's 30-minute precision. The weekly patterns
kept the same Europe/Belgrade wall-clock time across the October–November DST
transition, spanning two UTC offsets with no unknown conflicts. The coverage
counts are recorded in the calendar lifecycle report. These are development
functional checks completed before final acknowledgement-parser hardening;
exact staged-package acceptance remains pending.
